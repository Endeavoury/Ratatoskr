## Scope and effective-source rules

This profile constructs a single standard DNS `OPCODE=0` query and structurally parses a correlated response. It supports UDP and TCP, including TCP fallback after a truncated UDP response. It is not an authoritative server, recursive resolver, cache, DNSSEC validator, EDNS client, encrypted DNS client, mDNS/DNS-SD client, transfer/NOTIFY/UPDATE/DSO client, or binding design.

Effective sources are RFC 1034 §§3.1–3.3 and 5.3.1; RFC 1035 §§2.3.4, 3.1–3.3, 4.1–4.2.2; RFC 1123 §6.1.3 as updated by RFC 7766; RFC 2181 §§9–11; RFC 3425 §3; RFC 3597 §§2–5; RFC 4343 §§2–4; RFC 5452 §§4–6 and 9; RFC 7766 §§5–8; RFC 9619 §§3–5; and the IANA DNS Parameters registry for current numeric assignments. RFC 6891 governs an excluded extension and is used only to recognize OPT safely. RFC 9267 §§2–6 is non-normative, supporting hostile-input guidance. Held/rejected errata are not silently incorporated; RFC 9619 EID 8426 is editorial to the technical rule and RFC 7766 has no matching errata in the reviewed inventory.

## Wire and framing profile

A DNS message begins with the 12-octet header: ID (16), flags (16), QDCOUNT (16), ANCOUNT (16), NSCOUNT (16), ARCOUNT (16), all network byte order. Flags are `QR|OPCODE(4)|AA|TC|RD|RA|Z|AD|CD|RCODE(4)` under current IANA allocation. The profile always emits `QR=0`, `OPCODE=0`, `QDCOUNT=1`, and zero RR counts. It encodes `QNAME|QTYPE|QCLASS` exactly once.

Each response field is bounds checked before it is read. Name compression is a message-relative decoding rule, not a string substitution rule: the cursor in the parent RR/question advances over the encoded pointer while the resolver separately follows the pointed representation to obtain the logical name. RDLENGTH creates a strict subcursor for RDATA. Counts do not authorize allocation or reads by themselves. TCP adds a separate two-octet frame prefix; UDP does not.

## Error, recovery, and ownership profile

- **Local validation error:** invalid name, selected-type rejection, invalid options, or unavailable dependency; send nothing and retain no result.
- **Nonmatching response:** ignore and keep the request pending until deadline; never poison another transaction.
- **Malformed matching response:** terminate that transaction with `malformed_response`; discard all partially built records.
- **Resource-limit error:** terminate with `resource_limit`; no partial result. Exact limits remain a documented API decision, not invented protocol law.
- **Unsupported extension:** terminal `unsupported_extension` for OPT/EDNS response material. It is structurally distinct from malformed bytes.
- **DNS RCODE:** structurally valid, correlated response outcome; return response metadata/result according to later API design, with a distinct DNS-status classification. No cache or retry policy is implied.
- **UDP TC:** transition only to TCP fallback; do not surface truncated content.
- **Timeout/network/connect/EOF:** terminal transport error; retry and server rotation are outside this candidate until a product/API policy selects them.

Result publication is atomic. The eventual API must state whether a DNS nonzero RCODE is represented as a result, an error carrying result metadata, or both; it must not conflate it with parser/transport failure. All record and string/raw-RDATA views must have a single enclosing result owner and become invalid on result destruction.

## Security and resource implications

Parsing is hostile-input work. Pointer target, label length, name length, null termination, RDLENGTH and all four count fields need checked arithmetic and bounded cursors before allocation, indexing, dereference, or copy. RFC 9267 is supporting, not normative, evidence for these anti-patterns. Correlation checks require transaction context rather than ID-only lookup, random full-width IDs, source/destination/port binding, and case-insensitive QNAME matching. They mitigate but cannot provide cryptographic authenticity. TCP connection reuse, concurrent requests, deadlines, cancellation, and limits become security-relevant state if later enabled.

## Deferred/excluded behavior

No EDNS query construction, OPT option interpretation, extended RCODE representation, EDE, DNS Cookie, payload negotiation, DNSSEC validation, cache/negative-cache/serve-stale policy, recursive referral following, server selection, retry policy, authoritative service, AXFR/IXFR, UPDATE, NOTIFY, DSO, mDNS/DNS-SD, DoT/DoH/DoQ/DTLS, or binding work is approved. Unknown ordinary response RRs are opaque envelopes, not a commitment to support every registry type. A scope expansion requires its own source closure, analysis change, and renewed downstream gates.

## Required downstream evidence

The protocol model must encode the request context, framing accumulator, per-transport states, result/error domains, and atomic publication invariant. API design must expose owned-result lifetime, a request’s deadline/cancellation rules, error classification, resource configuration, and capability/exclusion disclosure. Vectors must cover exact valid header/query/RR bytes; every section; pointer and RDLENGTH/count failures; reserved bits; QDCOUNT; case/correlation/source mismatch; UDP TC→TCP; TCP fragmented/coalesced/out-of-order frames; nonzero RCODE; unknown RR; OPT; limits; timeout/EOF/cancellation. Security review and fuzzing must verify bounded parsing and no partial result under arbitrary bytes.
